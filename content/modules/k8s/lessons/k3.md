# Durcir un pod et fermer le réseau

Par défaut, Kubernetes est ouvert : un pod peut parler à tous les autres, tourner en root et monter le disque du nœud. Une faille dans une application devient alors une faille dans le cluster. Le durcissement referme ces portes.

## Le contexte de sécurité

Le **securityContext** règle les droits d'un **pod** ou d'un **conteneur**.

```yaml
spec:
  automountServiceAccountToken: false
  securityContext:
    runAsNonRoot: true
  containers:
    - name: web
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
```

`runAsNonRoot: true` refuse de démarrer un conteneur qui tourne en root. `allowPrivilegeEscalation: false` empêche un processus de gagner plus de droits que son parent. `readOnlyRootFilesystem: true` rend le système de fichiers non modifiable : un attaquant ne peut pas y déposer d'outil. `capabilities.drop: ["ALL"]` retire les pouvoirs spéciaux de Linux.

!!Un conteneur privileged: true a presque les droits de la machine hôte : n'en créez jamais sans raison documentée!!

!!Un cluster non durci n'est qu'un seul incident : activez ces réglages dès le premier déploiement, pas après la première alerte!!

## Ce qu'il faut éviter

`hostNetwork`, `hostPID` et les volumes `hostPath` relient le pod à la machine qui l'héberge : il peut alors voir son réseau, ses processus ou son disque.

## Le jeton du compte de service

Chaque pod reçoit par défaut un jeton pour parler à l'API Kubernetes. Une application web n'en a pas besoin : `automountServiceAccountToken: false` le retire, et un attaquant qui entre dans le pod n'a plus d'accès à l'API.

## Les politiques réseau

Une **NetworkPolicy** filtre le trafic entre pods. La bonne approche est la même que pour un pare-feu : tout refuser, puis autoriser. Une politique avec `podSelector: {}` et `policyTypes: ["Ingress"]` sans règle refuse toute entrée vers tous les pods du namespace. On ajoute ensuite une politique qui autorise précisément qui a le droit d'entrer.

!!Une politique allow-all annule toute la protection : désignez toujours l'émetteur et le port autorisés!!

**À retenir :** `runAsNonRoot`, pas d'escalade, système de fichiers en lecture seule, `drop ALL`, pas de `privileged` ni de `hostPath`, jeton du compte de service retiré, NetworkPolicy en refus par défaut.
