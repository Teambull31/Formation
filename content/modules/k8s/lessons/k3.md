# Durcir un pod et fermer le réseau

Par défaut, Kubernetes est ouvert : un pod peut parler à tous les autres, tourner en root et monter le disque du nœud. Une faille dans une application devient alors une faille dans le cluster. Le durcissement referme ces portes.

## Le contexte de sécurité

Le **securityContext** règle les droits d'un **pod** ou d'un **conteneur**. Il existe donc à **deux endroits**, et certains réglages n'existent qu'à l'un des deux. C'est la source d'erreur numéro un de ce chapitre.

```yaml
# Fichier : deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:                                   # ── niveau POD ──
      automountServiceAccountToken: false   # ← propriété du pod : aligné sur containers
      securityContext:                      # ← securityContext DU POD
        runAsNonRoot: true                  #   vaut pour tous les conteneurs du pod
      containers:
        - name: web                         # ── niveau CONTENEUR ──
          image: ghcr.io/example/web:1.4.2
          securityContext:                  # ← securityContext DU CONTENEUR, aligné sur image
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]                 # une liste : ["ALL"] ou un tiret par ligne
          volumeMounts:
            - name: tmp
              mountPath: /tmp               # lecture seule partout, sauf /tmp
      volumes:                              # ← niveau pod, aligné sur containers
        - name: tmp
          emptyDir: {}
```

Où va quoi :

| Réglage | Niveau | Pourquoi |
| --- | --- | --- |
| `automountServiceAccountToken` | pod | le jeton est monté une fois pour tout le pod |
| `runAsNonRoot` | pod (ou conteneur) | au pod, il s'applique à tous les conteneurs d'un coup |
| `allowPrivilegeEscalation` | conteneur seulement | il concerne un processus précis |
| `readOnlyRootFilesystem` | conteneur seulement | chaque conteneur a son propre système de fichiers |
| `capabilities` | conteneur seulement | idem |

`runAsNonRoot: true` refuse de démarrer un conteneur qui tourne en root. `allowPrivilegeEscalation: false` empêche un processus de gagner plus de droits que son parent. `readOnlyRootFilesystem: true` rend le système de fichiers non modifiable : un attaquant ne peut pas y déposer d'outil. `capabilities.drop: ["ALL"]` retire les pouvoirs spéciaux de Linux.

Une application qui écrit des fichiers temporaires échoue avec `readOnlyRootFilesystem`. La solution est dans l'exemple : un volume `emptyDir` monté sur `/tmp`, seul dossier inscriptible.

!!Un conteneur privileged: true a presque les droits de la machine hôte : n'en créez jamais sans raison documentée!!

!!Un cluster non durci n'est qu'un seul incident : activez ces réglages dès le premier déploiement, pas après la première alerte!!

## Ce qu'il faut éviter

`hostNetwork`, `hostPID` et les volumes `hostPath` relient le pod à la machine qui l'héberge : il peut alors voir son réseau, ses processus ou son disque.

## Le jeton du compte de service

Chaque pod reçoit par défaut un jeton pour parler à l'API Kubernetes. Une application web n'en a pas besoin : `automountServiceAccountToken: false` le retire, et un attaquant qui entre dans le pod n'a plus d'accès à l'API.

## Les politiques réseau

Une **NetworkPolicy** filtre le trafic entre pods. La bonne approche est la même que pour un pare-feu : tout refuser, puis autoriser. Une politique avec `podSelector: {}` et `policyTypes: ["Ingress"]` sans règle refuse toute entrée vers tous les pods du namespace. On ajoute ensuite une politique qui autorise précisément qui a le droit d'entrer.

```yaml
# Fichier : networkpolicy.yaml
# ── Politique 1 : tout refuser ──
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all
spec:
  podSelector: {}               # {} = tous les pods du namespace
  policyTypes: ["Ingress"]      # on filtre le trafic entrant…
                                # …et sans bloc ingress, rien n'est autorisé
---
# ── Politique 2 : autoriser gateway vers web sur 8000 ──
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: gateway-to-web
spec:
  podSelector:                  # QUI est protégé : les pods destinataires
    matchLabels:
      app: web
  policyTypes: ["Ingress"]
  ingress:                      # la liste des entrées autorisées
    - from:                     # une règle : d'où…
        - podSelector:
            matchLabels:
              app: gateway      # …depuis les pods gateway
      ports:                    # aligné sur from : MÊME règle
        - port: 8000
          protocol: TCP
```

Le piège d'indentation est sur `ports:`. Aligné sur `from:`, il appartient à la même règle : « depuis gateway **et** sur le port 8000 ». Si vous ajoutez un tiret devant `ports:`, il devient une **seconde** règle : « depuis gateway, sur tous les ports » **ou** « depuis n'importe où, sur le port 8000 ». Une seule espace ou un tiret de trop ouvre le service à tout le cluster.

```yaml
# FAUX : deux règles distinctes, le port 8000 est ouvert à tous
  ingress:
    - from:
        - podSelector: {matchLabels: {app: gateway}}
    - ports:
        - port: 8000

# JUSTE : une seule règle, les deux conditions ensemble
  ingress:
    - from:
        - podSelector: {matchLabels: {app: gateway}}
      ports:
        - port: 8000
```

!!Une politique allow-all annule toute la protection : désignez toujours l'émetteur et le port autorisés!!

## Pas à pas : durcir le Deployment et le réseau

1. Dans `deployment.yaml`, trouvez le `spec:` du pod (sous `template:`). Ajoutez-y `automountServiceAccountToken: false` et `securityContext:` avec `runAsNonRoot: true`, alignés sur `containers:`.
2. Dans le conteneur, aligné sur `image:`, ajoutez son propre `securityContext:` avec `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem: true` et `capabilities:` / `drop: ["ALL"]`.
3. Videz `networkpolicy.yaml` et écrivez la politique `deny-all` : `podSelector: {}`, `policyTypes: ["Ingress"]`, pas de bloc `ingress`.
4. Écrivez `---`, puis la politique `gateway-to-web` : `podSelector` sur `app: web`, et une seule règle `ingress` avec `from` (pods `app: gateway`) et `ports` (8000) alignés.
5. Validez avec `kubeconform -strict deployment.yaml networkpolicy.yaml`.
6. Avec kind : `kubectl apply -f .`, puis `kubectl describe networkpolicy gateway-to-web` relit la règle telle que le cluster l'a comprise.

**À retenir :** `runAsNonRoot` et jeton au niveau du pod, pas d'escalade, lecture seule et `drop ALL` au niveau du conteneur, pas de `privileged` ni de `hostPath`, NetworkPolicy en refus par défaut, `from` et `ports` dans la même règle.
