# Kustomize, Helm et RBAC : livrer par environnement

Le même service tourne en dev, en préproduction et en production, avec quelques différences : nombre de réplicas, version de l'image, namespace. Copier trois fois les manifestes garantit qu'ils divergeront. Et le robot qui déploie ne doit pas avoir les clés de tout le cluster.

## Kustomize : une base, des surcouches

Kustomize est intégré à `kubectl` (`kubectl apply -k`). Il part d'une **base** commune et applique des **overlays** par environnement, sans gabarit ni variable.

```
base/
  deployment.yaml
  service.yaml
  kustomization.yaml
overlays/
  prod/
    kustomization.yaml
```

```yaml
# base/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yaml
  - service.yaml
```

```yaml
# overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: prod
resources:
  - ../../base
images:
  - name: registry.example.test/web
    newTag: "1.5.0"
replicas:
  - name: web
    count: 3
```

Comment ces fichiers se relient :

- `resources:` de la base liste les fichiers **du même dossier** : `deployment.yaml`, pas `base/deployment.yaml`.
- `resources:` de l'overlay pointe vers un **dossier** : `../../base` remonte de `overlays/prod/` à la racine, puis descend dans `base/`. Kustomize y lit le `kustomization.yaml`.
- `images[].name` doit être le nom d'image **exact** de la base, sans le tag : c'est une recherche, et un nom différent ne remplace rien, sans erreur.
- `replicas[].name` est le `metadata.name` du Deployment, pas le nom du conteneur.
- `namespace:` est au niveau 0 de l'overlay : il s'applique à toutes les ressources produites.

Voici ce que produit l'overlay sur le Deployment de la base (extrait de `kubectl kustomize overlays/prod`) :

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: prod                               # ajouté par « namespace: prod »
spec:
  replicas: 3                                   # remplacé par « replicas »
  template:
    spec:
      containers:
        - name: web
          image: registry.example.test/web:1.5.0   # tag remplacé par « images »
```

`kubectl kustomize overlays/prod` affiche le résultat final sans rien appliquer : c'est la commande à lancer avant chaque revue. Pour un changement plus fin, `patches:` applique un morceau de YAML sur une ressource de la base.

!!Le tag de l'image se fixe dans l'overlay de chaque environnement : jamais latest, sinon prod et préprod ne tournent pas la même version!!

## Helm : le gestionnaire de paquets

**Helm** emballe une application dans un **chart** : des gabarits (`templates/`) et des valeurs par défaut (`values.yaml`). On installe un chart comme un paquet :

```bash
helm repo add bitnami https://charts.bitnami.com/bitnami
helm upgrade --install cache bitnami/redis --version 19.6.4 -f values-prod.yaml -n prod
helm history cache -n prod
helm rollback cache 2 -n prod
```

Règle pratique : **Helm pour installer des logiciels tiers** (une base, un contrôleur d'Ingress, Prometheus), **Kustomize pour vos propres services**. Épinglez toujours `--version` du chart.

!!Sans --version, Helm installe la dernière version du chart : une mise à jour majeure peut arriver sans prévenir!!

## GitOps

Avec **Argo CD** ou **Flux**, un agent dans le cluster lit le dépôt Git et applique ce qui y est écrit. Le dépôt devient la source de vérité : un retour arrière, c'est un `git revert`. La CI ne pousse plus vers le cluster, elle met à jour le tag dans l'overlay.

## RBAC : qui peut faire quoi

Toute requête à l'API Kubernetes est autorisée par le **RBAC** :

- un **Role** liste des droits dans **un** namespace ; un **ClusterRole** vaut pour tout le cluster ;
- un **RoleBinding** donne un Role à un sujet : utilisateur, groupe ou **ServiceAccount** (l'identité d'un robot ou d'un pod).

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: deployer
  namespace: prod
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: deployer
  namespace: prod
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch", "update", "patch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: deployer
  namespace: prod
subjects:
  - kind: ServiceAccount
    name: deployer
    namespace: prod
roleRef:
  kind: Role
  name: deployer
  apiGroup: rbac.authorization.k8s.io
```

Les trois objets forment une chaîne, reliée par les noms :

```
ServiceAccount deployer (ns prod) ◄── subjects[0] ──┐
                                                     RoleBinding deployer (ns prod)
Role deployer (ns prod)          ◄── roleRef ───────┘
```

- Le RoleBinding est le seul à connaître les deux autres : `subjects` désigne **qui**, `roleRef` désigne **quels droits**.
- Les trois sont dans le même namespace : un RoleBinding ne donne des droits que dans son propre namespace.
- `subjects` est une liste (tiret), `roleRef` est un seul objet (pas de tiret) : un RoleBinding donne un seul Role, à un ou plusieurs sujets.
- `apiGroups: ["apps"]` vient de l'`apiVersion: apps/v1` des Deployments. Pour les objets du groupe de base (pods, services, secrets), on écrit `apiGroups: [""]`.

!!Lier cluster-admin au compte de service d'une CI donne le cluster entier à quiconque compromet le pipeline!!

Pièges du RBAC :

- `verbs: ["*"]` ou `resources: ["*"]` : tous les droits, y compris ceux qui n'existent pas encore.
- Lire les `secrets` d'un namespace revient à lire tous ses mots de passe.
- Le droit de créer des pods permet de monter n'importe quel Secret du namespace : c'est un droit fort.

Vérifier un droit sans deviner :

```bash
kubectl auth can-i update deployments -n prod --as=system:serviceaccount:prod:deployer
kubectl auth can-i get secrets -n prod --as=system:serviceaccount:prod:deployer
```

## Pas à pas : livrer en production avec un robot limité

1. Dans `base/kustomization.yaml`, sous `resources:`, listez `- deployment.yaml` et `- service.yaml`.
2. Dans `overlays/prod/kustomization.yaml`, au niveau 0 : `apiVersion`, `kind: Kustomization`, `namespace: prod`.
3. Ajoutez `resources:` avec `- ../../base`.
4. Ajoutez `images:` avec un élément : `name: registry.example.test/web` et `newTag: "1.5.0"` (guillemets : c'est un texte).
5. Ajoutez `replicas:` avec un élément : `name: web` et `count: 3`.
6. Contrôlez le résultat : `kubectl kustomize overlays/prod`, et vérifiez le namespace, le tag et les réplicas.
7. Dans `rbac.yaml`, supprimez le ClusterRoleBinding. Écrivez le ServiceAccount, puis `---`, le Role avec ses cinq verbes sur `deployments` du groupe `apps`, puis `---`, le RoleBinding qui les relie.
8. Avec un cluster : `kubectl auth can-i update deployments -n prod --as=system:serviceaccount:prod:deployer` répond `yes`, et la même question pour `delete` répond `no`.

## Labo réel (optionnel)

```bash
kubectl kustomize overlays/prod | less
kubectl apply -k overlays/prod
kubectl apply -f rbac.yaml
kubectl auth can-i delete namespaces --as=system:serviceaccount:prod:deployer   # doit répondre no
```

**À retenir :** base et overlays Kustomize, `kubectl kustomize` avant d'appliquer, image et réplicas fixés par overlay ; Helm pour les logiciels tiers avec `--version` ; GitOps : Git est la vérité ; RBAC en Role et RoleBinding dans un namespace, verbes listés, pas de `*`, pas de `cluster-admin`, vérification par `kubectl auth can-i`.
