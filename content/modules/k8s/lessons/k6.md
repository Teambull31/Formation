# Dépanner un cluster : lire les symptômes

Un expert Kubernetes ne connaît pas toutes les options par cœur : il sait **lire les symptômes** et remonter à la cause en trois commandes. Cette leçon est une méthode, le TP est une garde de nuit avec cinq incidents.

## La méthode en quatre commandes

```bash
kubectl get pods -o wide             # l'état, les redémarrages, le nœud
kubectl describe pod <pod>            # la configuration et surtout les Events en bas
kubectl logs <pod> --previous         # le journal du conteneur AVANT le dernier crash
kubectl get events --sort-by=.lastTimestamp
```

On lit toujours dans cet ordre : **l'état**, puis **les événements**, puis **les journaux**. La colonne `STATUS` dit dans quelle famille chercher.

!!kubectl logs sans --previous montre le conteneur qui vient de redémarrer, souvent vide : la vraie erreur est dans le journal précédent!!

## Les cinq pannes classiques

### ImagePullBackOff / ErrImagePull

Le nœud n'arrive pas à télécharger l'image. Dans les Events : `Failed to pull image ... not found` ou `unauthorized`.

- tag mal écrit ou inexistant ;
- registre privé sans `imagePullSecrets` ;
- nom de registre erroné.

### CrashLoopBackOff

Le conteneur démarre puis s'arrête, encore et encore ; Kubernetes espace les tentatives (10 s, 20 s, 40 s... jusqu'à 5 min). La cause est **dans l'application** : lisez `kubectl logs --previous`. Le plus souvent : variable d'environnement manquante, fichier de configuration absent, base injoignable, mauvaise commande.

### Pending

Le pod n'a pas de nœud. Les Events disent pourquoi : `0/3 nodes are available: 3 Insufficient memory` (demande trop grosse), `didn't match Pod's node affinity`, `had untolerated taint`, ou un PVC qui ne trouve pas de volume (`unbound immediate PersistentVolumeClaims`).

!!Un pod Pending ne produit aucun journal : inutile de lancer kubectl logs, la réponse est dans les Events!!

### OOMKilled (code 137)

Le conteneur a dépassé sa `limits.memory` ; le noyau l'a tué. `kubectl describe` affiche `Last State: Terminated, Reason: OOMKilled, Exit Code: 137`. Remède : augmenter la limite si l'application en a réellement besoin, ou corriger la fuite mémoire.

Retenez les codes de sortie : `137` = tué par signal 9 (souvent OOM), `143` = arrêté proprement par SIGTERM, `1` = erreur de l'application.

### Service sans endpoints

Les pods tournent, mais le Service ne répond pas. `kubectl get endpoints web` affiche `<none>` : le **sélecteur** du Service ne correspond aux étiquettes d'aucun pod prêt. Comparez `kubectl get svc web -o yaml` et `kubectl get pods --show-labels`.

## Autres outils du dépanneur

- `kubectl exec -it <pod> -- sh` : entrer dans le conteneur (s'il a un shell).
- `kubectl debug -it <pod> --image=busybox:1.36 --target=<conteneur>` : un conteneur de débogage éphémère, quand l'image n'a pas de shell.
- `kubectl port-forward svc/web 8080:80` : tester un Service depuis votre poste.
- `kubectl run tmp --rm -it --image=busybox:1.36 -- wget -qO- http://web` : tester depuis l'intérieur du cluster.
- `kubectl top pods` : consommation réelle (avec metrics-server).

## Corriger au bon endroit

On ne corrige pas un incident avec `kubectl edit` en production sans reporter la correction dans le dépôt : au prochain déploiement, l'erreur revient. La correction se fait dans le **manifeste versionné**, puis on applique.

!!Une correction faite à la main dans le cluster et absente du dépôt sera écrasée au prochain déploiement!!

## Labo réel (optionnel)

Avec kind, appliquez le fichier `manifests.yaml` du TP **avant** de le corriger, et observez chaque panne avec la méthode ci-dessus. Puis appliquez votre version corrigée.

**À retenir :** état, événements, journaux, dans cet ordre ; `logs --previous` ; ImagePullBackOff = image, CrashLoopBackOff = application, Pending = planification, OOMKilled = mémoire, endpoints vides = sélecteur ; code 137 ; correction dans le dépôt, pas à la main.
