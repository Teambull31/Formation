# Pods, Deployments et étiquettes

Kubernetes décrit un état voulu : « je veux deux copies de cette application ». Le cluster compare sans cesse cet état à la réalité et corrige l'écart. Vous déclarez, il exécute.

## Le pod et le Deployment

Un **pod** est la plus petite unité : un ou plusieurs conteneurs qui partagent le réseau et le stockage. On ne crée presque jamais de pod seul. Un **Deployment** déclare combien de copies d'un pod garder en vie et comment les mettre à jour : si un pod meurt, il en recrée un.

## Les quatre rubriques de tout manifeste

Tout objet Kubernetes, quel que soit son type, commence par les mêmes quatre clés au **niveau 0** :

| Clé | Rôle | Exemple |
| --- | --- | --- |
| `apiVersion` | la version de l'API qui connaît ce type | `apps/v1` pour un Deployment, `v1` pour un Service |
| `kind` | le type d'objet | `Deployment`, `Service`, `ConfigMap` |
| `metadata` | son identité : nom, étiquettes | `name: web` |
| `spec` | l'état voulu, propre à chaque type | `replicas`, `selector`, `template` |

## Le Deployment complet, ligne par ligne

Un Deployment contient un **modèle de pod** (`template`), et ce modèle a lui-même un `metadata` et un `spec`. C'est pourquoi on voit deux fois ces mots : une fois pour le Deployment, une fois pour le pod qu'il fabrique.

```yaml
# Fichier : deployment.yaml
apiVersion: apps/v1                 # niveau 0
kind: Deployment                    # niveau 0
metadata:                           # niveau 0 : identité DU DEPLOYMENT
  name: web
spec:                               # niveau 0 : ce que veut le Deployment
  replicas: 2                       # niveau 1 : combien de pods
  selector:                         # niveau 1 : comment il reconnaît SES pods
    matchLabels:
      app: web                      # ← doit être identique à la ligne ① plus bas
  template:                         # niveau 1 : le modèle de pod à fabriquer
    metadata:                       # niveau 2 : identité DE CHAQUE POD
      labels:
        app: web                    # ① l'étiquette posée sur chaque pod
    spec:                           # niveau 2 : contenu DE CHAQUE POD
      containers:                   # niveau 3 : une liste de conteneurs
        - name: web                 # niveau 4 : le tiret ouvre un conteneur
          image: ghcr.io/example/web:1.4.2   # aligné sur name : même conteneur
          ports:
            - containerPort: 8000
          resources:                # aligné sur image : propriété du conteneur
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 256Mi
```

Repères pour ne pas se perdre :

- Les deux `spec` n'ont pas le même rôle : le premier (niveau 0) parle du Deployment, le second (sous `template`) parle du pod.
- `containers` est une **liste** : chaque conteneur commence par `- `. Ses propriétés (`image`, `ports`, `resources`) s'alignent sur `name`, pas sur le tiret.
- `resources` appartient au **conteneur**, pas au pod ni au Deployment : chaque conteneur a ses propres besoins.

## Les étiquettes et le sélecteur

Les **étiquettes** (labels) sont des paires clé-valeur posées sur les objets. Le `selector` du Deployment dit « mes pods sont ceux qui portent ces étiquettes ». Il doit correspondre aux étiquettes du modèle de pod (`template.metadata.labels`) : sinon le Deployment ne retrouve pas ses propres pods.

```yaml
# FAUX : le sélecteur cherche app: web, le modèle pose app: frontend
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: frontend

# JUSTE : la même paire clé-valeur des deux côtés
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
```

!!Un sélecteur qui ne correspond pas au modèle de pod est refusé par le cluster, ou pire, adopte des pods qui ne sont pas les siens!!

## Plusieurs réplicas

Avec `replicas: 1`, la perte du nœud qui l'héberge coupe le service le temps d'un redémarrage. Avec au moins deux, le cluster répartit les pods et le service survit à la panne d'une machine. `replicas` est au niveau 1, sous le premier `spec` : c'est le Deployment qui compte les pods, pas le pod lui-même.

## Épingler l'image

Comme pour Docker, `image: web:latest` ne dit pas quelle version tourne. Un tag précis rend les déploiements reproductibles et les retours en arrière possibles.

!!N'utilisez jamais le tag latest dans un manifeste : un redémarrage peut tirer une version que personne n'a testée!!

## Demander des ressources

`resources.requests` indique ce dont le pod a besoin : le planificateur s'en sert pour choisir un nœud. `resources.limits` fixe le plafond : un pod qui dépasse la mémoire autorisée est arrêté. Les unités : `100m` est un dixième de cœur, `128Mi` environ 134 Mo.

`requests` et `limits` sont deux clés sœurs sous `resources`, et chacune contient `cpu` **et** `memory`. La limite est toujours supérieure ou égale à la demande.

!!Un pod sans limite peut avaler toute la mémoire d'un nœud et faire tomber ses voisins!!

## Pas à pas : écrire et appliquer un Deployment

1. Créez `deployment.yaml` et écrivez les quatre rubriques au niveau 0 : `apiVersion: apps/v1`, `kind: Deployment`, `metadata:` avec `name:`, `spec:`.
2. Sous `spec:` (2 espaces) : `replicas: 2`, puis `selector:` / `matchLabels:` / `app: web`.
3. Toujours sous `spec:`, ajoutez `template:`, puis dedans `metadata:` / `labels:` / `app: web`, la même paire que le sélecteur.
4. Sous `template:`, ajoutez le second `spec:`, puis `containers:` et un premier conteneur `- name: web`.
5. Alignées sur `name`, ajoutez `image:` avec un tag précis, `ports:` avec `- containerPort: 8000`, et `resources:` avec `requests` et `limits`.
6. Validez sans cluster : `kubeconform -strict deployment.yaml`.
7. Avec un cluster (kind) : `kubectl apply -f deployment.yaml`, puis `kubectl get pods -l app=web` montre deux pods.
8. Supprimez un pod (`kubectl delete pod <nom>`) et relancez `kubectl get pods` : le Deployment en a recréé un.

**À retenir :** pod, Deployment, quatre rubriques `apiVersion` `kind` `metadata` `spec`, deux niveaux de `spec`, étiquettes et `selector` concordants, tag précis, `requests` et `limits` dans le conteneur.
