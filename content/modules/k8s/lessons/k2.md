# Services, configuration et sondes

Un pod est éphémère : son adresse change à chaque recréation. Pour qu'une application soit joignable, configurée proprement et surveillée, Kubernetes ajoute trois mécanismes.

## Le fichier complet

Voici le fichier d'arrivée : trois objets séparés par `---`. Chaque section de la leçon explique un bloc, et surtout **où** il s'insère dans le Deployment.

```yaml
# Fichier : app.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: web-config
data:                              # niveau 0 : les paires clé-valeur
  APP_MODE: production
---                                # ← sépare deux objets dans un même fichier
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: ghcr.io/example/web:1.4.2
          ports:
            - containerPort: 8000
          env:                                 # ← propriété du conteneur, alignée sur image
            - name: APP_MODE                   # une variable = un élément de liste
              valueFrom:                       # aligné sur name : même variable
                configMapKeyRef:
                  name: web-config             # le ConfigMap ci-dessus
                  key: APP_MODE                # la clé dans son data
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: web-db                 # un Secret créé à part, jamais versionné
                  key: password
          readinessProbe:                      # ← propriété du conteneur, alignée sur env
            httpGet:
              path: /healthz
              port: 8000
          livenessProbe:                       # ← même niveau que readinessProbe
            httpGet:
              path: /healthz
              port: 8000
            initialDelaySeconds: 10            # ← aligné sur httpGet, PAS dessous
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web                       # ← mêmes étiquettes que les pods du Deployment
  ports:
    - port: 80                     # le port du Service
      targetPort: 8000             # le port du conteneur
```

Le fil conducteur : `env`, `readinessProbe` et `livenessProbe` sont des propriétés **du conteneur**. Elles s'alignent donc sur `name:`, `image:` et `ports:` du conteneur, à 10 espaces dans ce fichier. Les écrire ailleurs (sous le pod ou sous le Deployment) les rend invalides.

## Le Service

Un **Service** donne une adresse stable devant un groupe de pods. Il les retrouve par le même mécanisme d'étiquettes : son `selector` désigne les pods cibles, `port` est le port exposé, `targetPort` celui du conteneur. Par défaut le type est `ClusterIP` : joignable seulement depuis l'intérieur du cluster.

Le trajet d'une requête : un client appelle `web:80` ; le Service choisit un pod portant `app: web` ; il transmet au port `8000` de ce pod, celui du `containerPort`.

Attention, le sélecteur d'un Service s'écrit **directement** sous `selector:`, sans `matchLabels:`. Celui d'un Deployment, lui, a besoin de `matchLabels:`. C'est une différence historique entre les deux API.

!!Un sélecteur de Service qui ne correspond à aucun pod ne produit aucune erreur : le service existe mais ne route nulle part!!

## ConfigMap : la configuration

Un **ConfigMap** stocke de la configuration non secrète, hors de l'image. Le conteneur la lit avec `valueFrom: configMapKeyRef` : on change de configuration sans reconstruire l'image.

Une variable d'environnement a deux formes, et `value` et `valueFrom` ne vont jamais ensemble :

```yaml
          env:
            - name: LOG_LEVEL
              value: info                # valeur écrite en dur
            - name: APP_MODE
              valueFrom:                 # valeur lue ailleurs
                configMapKeyRef:
                  name: web-config
                  key: APP_MODE
```

## Secret : les valeurs sensibles

Un **Secret** est fait pour les mots de passe et les jetons. Le pod le référence avec `valueFrom: secretKeyRef` (nom du Secret, clé). Le manifeste du Deployment ne contient alors jamais la valeur.

On crée le Secret par une commande, pas dans un fichier versionné :

```bash
kubectl create secret generic web-db --from-literal=password='une-valeur-longue'
```

!!Ne versionnez jamais un Secret avec ses valeurs : les données y sont encodées en base64, pas chiffrées!!

## Les sondes

Une **sonde de disponibilité** (`readinessProbe`) dit si le pod peut recevoir du trafic : tant qu'elle échoue, le Service ne lui envoie rien. Une **sonde de vivacité** (`livenessProbe`) dit si le pod est bloqué : en cas d'échec, Kubernetes le redémarre.

`initialDelaySeconds` laisse à l'application le temps de démarrer avant les premiers tests. Trop court, et Kubernetes tue en boucle une application qui n'a pas fini de démarrer.

L'erreur d'indentation classique : mettre `initialDelaySeconds` sous `httpGet`. Ce réglage concerne la **sonde**, pas la requête HTTP.

```yaml
# FAUX : initialDelaySeconds est pris pour un champ de httpGet, refusé
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8000
              initialDelaySeconds: 10

# JUSTE : aligné sur httpGet, c'est un réglage de la sonde
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8000
            initialDelaySeconds: 10
```

!!Une sonde de vivacité trop sévère redémarre en boucle une application saine mais lente : réglez-la avec prudence!!

## Pas à pas : rendre l'application exploitable

1. Ouvrez `app.yaml` et repérez le conteneur : la ligne `- name: web` sous `containers:`. Tout ce qui suit s'aligne sur ce `name`.
2. Sous le conteneur, dans `env:`, remplacez la valeur de `APP_MODE` par un bloc `valueFrom:` / `configMapKeyRef:` avec `name: web-config` et `key: APP_MODE`.
3. Faites de même pour `DB_PASSWORD` avec `secretKeyRef:`, `name: web-db`, `key: password`. Supprimez la ligne `value:`.
4. Toujours aligné sur `env:`, ajoutez `readinessProbe:` avec `httpGet:` (`path: /healthz`, `port: 8000`).
5. Ajoutez `livenessProbe:` de la même façon, puis `initialDelaySeconds: 10` aligné sur son `httpGet:`.
6. En fin de fichier, écrivez `---` seul sur sa ligne, puis le Service : `selector:` avec `app: web`, et `ports:` avec `port: 80` et `targetPort: 8000`.
7. Validez avec `kubeconform -strict app.yaml`. Avec un cluster : `kubectl apply -f app.yaml`, puis `kubectl get endpoints web` doit lister les adresses des pods.

**À retenir :** Service avec sélecteur et `targetPort`, ConfigMap, Secret par référence, `env` et sondes au niveau du conteneur, sondes de disponibilité et de vivacité, délai initial aligné sur `httpGet`.
