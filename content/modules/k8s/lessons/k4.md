# Stockage, StatefulSet et tâches planifiées

Un pod est jetable : quand il redémarre, tout ce qu'il a écrit sur son disque disparaît. Pour une application web sans état, c'est parfait. Pour une base de données, c'est une catastrophe. Cette leçon couvre ce qui doit survivre au pod, et ce qui tourne à heure fixe.

## Volumes : de l'éphémère au persistant

- `emptyDir` : un dossier vide créé avec le pod, détruit avec lui. Bon pour un cache ou un fichier temporaire.
- `configMap` / `secret` montés en fichiers : de la configuration en lecture.
- **PersistentVolumeClaim** (PVC) : une demande de disque durable. Le pod peut mourir et renaître sur un autre nœud, le disque le suit.

!!Une base de données sur un volume emptyDir perd toutes ses données au premier redémarrage du pod!!

## Un volume se déclare, puis se monte

Dans un pod, un volume apparaît toujours **deux fois**, reliées par le même nom :

- `volumes:` au niveau du **pod** (aligné sur `containers:`) : on dit d'où vient le volume ;
- `volumeMounts:` au niveau du **conteneur** (aligné sur `image:`) : on dit où il apparaît dans ce conteneur.

```yaml
    spec:                           # pod
      containers:
        - name: app
          image: ghcr.io/example/app:2.0.1
          volumeMounts:             # ← conteneur : OÙ le voir
            - name: cache           #   même nom que plus bas
              mountPath: /var/cache/app
      volumes:                      # ← pod : D'OÙ il vient
        - name: cache
          emptyDir: {}
```

## PV, PVC et StorageClass

Le développeur écrit un **PVC** : « je veux 10 Go en lecture-écriture ». Le cluster répond avec un **PersistentVolume** (PV), créé à la demande par une **StorageClass** (un disque cloud, un partage réseau). On ne manipule presque jamais les PV à la main.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 10Gi
```

`ReadWriteOnce` : un seul nœud monte le disque en écriture, le cas normal d'une base. `ReadWriteMany` exige un stockage partagé (NFS, CephFS).

## Le StatefulSet

Un Deployment considère ses pods comme interchangeables. Un **StatefulSet** leur donne une identité stable :

- des noms fixes : `db-0`, `db-1`, et non des suffixes aléatoires ;
- un disque par pod, recréé avec le même nom grâce à `volumeClaimTemplates` ;
- un ordre de démarrage et d'arrêt : `db-0` avant `db-1`.

```yaml
# Fichier : db.yaml (partie 1)
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db                   # ← niveau 1 : le Service headless défini plus bas
  replicas: 1
  selector:
    matchLabels:
      app: db
  template:
    metadata:
      labels:
        app: db
    spec:
      containers:
        - name: postgres
          image: postgres:16.4
          env:
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-secret
                  key: password
          volumeMounts:
            - name: data                          # ← même nom que le modèle ci-dessous
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:             # ← niveau 1, aligné sur template, PAS dedans
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 10Gi
```

Pourquoi `volumeClaimTemplates` est-il au niveau 1, à côté de `template`, et non dans le pod ? Parce que ce n'est pas le pod qui crée le disque, c'est le **StatefulSet** : il fabrique un PVC `data-db-0` pour le pod `db-0`, et le lui redonne s'il renaît. Ici, il n'y a donc **pas** de bloc `volumes:` dans le pod : le modèle de PVC le remplace.

Le nom du `volumeMounts` doit être celui du modèle de `volumeClaimTemplates`. Supprimer le StatefulSet ne supprime **pas** les PVC : les données restent, c'est voulu.

## Le Service headless

`serviceName: db` désigne un Service **headless** (`clusterIP: None`) : au lieu d'une adresse virtuelle unique, il publie un nom DNS par pod, `db-0.db`. Les bases répliquées s'en servent pour se trouver entre elles.

```yaml
# Fichier : db.yaml (partie 2)
---
apiVersion: v1
kind: Service
metadata:
  name: db                  # ← le nom cité par serviceName
spec:
  clusterIP: None           # ← « headless » : un nom DNS par pod
  selector:
    app: db
  ports:
    - port: 5432
```

!!Le serviceName d'un StatefulSet doit pointer vers un Service headless existant, sinon les noms DNS des pods n'existent pas!!

## Job et CronJob

Un **Job** lance des pods jusqu'à ce qu'ils réussissent une fois. Un **CronJob** crée un Job selon un horaire cron, comme une sauvegarde nocturne.

Un CronJob est un emboîtement de trois objets : le CronJob contient un modèle de Job (`jobTemplate`), qui contient un modèle de pod (`template`). Chaque réglage va au niveau de l'objet qu'il concerne.

```yaml
# Fichier : db.yaml (partie 3)
---
apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup
spec:                                   # ── niveau CRONJOB : quand et combien ──
  schedule: "0 3 * * *"                 # minute heure jour mois jour-semaine : 3 h chaque nuit
  concurrencyPolicy: Forbid             # jamais deux sauvegardes en même temps
  jobTemplate:
    spec:                               # ── niveau JOB : combien d'essais, combien de temps ──
      backoffLimit: 2
      activeDeadlineSeconds: 3600
      template:
        spec:                           # ── niveau POD : quoi exécuter ──
          restartPolicy: OnFailure
          containers:
            - name: dump
              image: postgres:16.4
              command: ["sh", "-c", "pg_dump -h db-0.db -U app app > /backup/app.sql"]
```

- `concurrencyPolicy: Forbid` : si la sauvegarde d'hier tourne encore, on n'en lance pas une deuxième. Réglage du **CronJob**, car c'est lui qui lance les Jobs.
- `backoffLimit` : nombre de nouvelles tentatives avant d'abandonner. Réglage du **Job**.
- `activeDeadlineSeconds` : durée maximale, un Job bloqué est tué. Réglage du **Job**.
- `restartPolicy` vaut `OnFailure` ou `Never` : jamais `Always` dans un Job. Réglage du **pod**.

L'expression cron se met entre guillemets : sans eux, YAML lit le `*` comme un caractère spécial et refuse le fichier.

!!Sans concurrencyPolicy: Forbid, une sauvegarde lente peut se chevaucher avec la suivante et saturer la base!!

## Pas à pas : passer la base en StatefulSet

1. Dans `db.yaml`, remplacez `kind: Deployment` par `kind: StatefulSet`, et ajoutez `serviceName: db` sous `spec:`.
2. Supprimez le bloc `volumes:` avec `emptyDir` dans le pod.
3. Au niveau 1, aligné sur `template:`, ajoutez `volumeClaimTemplates:` avec un modèle nommé `data` (`ReadWriteOnce`, `10Gi`).
4. Vérifiez que le `volumeMounts` du conteneur porte le nom `data` et le chemin `/var/lib/postgresql/data`.
5. Remplacez le mot de passe en clair par `valueFrom:` / `secretKeyRef:`, et épinglez l'image.
6. Après `---`, ajoutez le Service `db` avec `clusterIP: None` et le sélecteur `app: db`.
7. Dans le CronJob, placez chaque réglage à son niveau : `schedule` et `concurrencyPolicy` sous le premier `spec`, `backoffLimit` et `activeDeadlineSeconds` sous `jobTemplate.spec`, `restartPolicy` sous le `spec` du pod.
8. Validez avec `kubeconform -strict db.yaml`.

## Labo réel (optionnel)

Avec **kind** installé (`kind create cluster`) :

```bash
kubectl apply -f db.yaml
kubectl get statefulset,pvc,pods
kubectl delete pod db-0        # le pod revient avec le même nom et le même disque
kubectl get pvc                 # data-db-0 est toujours là
kubectl create job --from=cronjob/backup backup-manuel
```

**À retenir :** `emptyDir` meurt avec le pod, un volume se déclare au pod et se monte au conteneur, PVC pour les données durables, StatefulSet avec `volumeClaimTemplates` au niveau 1 et `volumeMounts` du même nom, Service headless, CronJob à trois niveaux avec `concurrencyPolicy: Forbid`, `backoffLimit` et `activeDeadlineSeconds`.
