# Stockage, StatefulSet et tâches planifiées

Un pod est jetable : quand il redémarre, tout ce qu'il a écrit sur son disque disparaît. Pour une application web sans état, c'est parfait. Pour une base de données, c'est une catastrophe. Cette leçon couvre ce qui doit survivre au pod, et ce qui tourne à heure fixe.

## Volumes : de l'éphémère au persistant

- `emptyDir` : un dossier vide créé avec le pod, détruit avec lui. Bon pour un cache ou un fichier temporaire.
- `configMap` / `secret` montés en fichiers : de la configuration en lecture.
- **PersistentVolumeClaim** (PVC) : une demande de disque durable. Le pod peut mourir et renaître sur un autre nœud, le disque le suit.

!!Une base de données sur un volume emptyDir perd toutes ses données au premier redémarrage du pod!!

## PV, PVC et StorageClass

Le développeur écrit un **PVC** : « je veux 10 Go en lecture-écriture ». Le cluster répond avec un **PersistentVolume** (PV), créé à la demande par une **StorageClass** (un disque cloud, un partage réseau). On ne manipule presque jamais les PV à la main.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 10Gi
```

`ReadWriteOnce` : un seul nœud monte le disque en écriture, le cas normal d'une base. `ReadWriteMany` exige un stockage partagé (NFS, CephFS).

## Le StatefulSet

Un Deployment considère ses pods comme interchangeables. Un **StatefulSet** leur donne une identité stable :

- des noms fixes : `db-0`, `db-1`, et non des suffixes aléatoires ;
- un disque par pod, recréé avec le même nom grâce à `volumeClaimTemplates` ;
- un ordre de démarrage et d'arrêt : `db-0` avant `db-1`.

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db
  replicas: 1
  selector:
    matchLabels:
      app: db
  template:
    metadata:
      labels:
        app: db
    spec:
      containers:
        - name: postgres
          image: postgres:16.4
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 10Gi
```

Le nom du `volumeMounts` doit être celui du modèle de `volumeClaimTemplates`. Supprimer le StatefulSet ne supprime **pas** les PVC : les données restent, c'est voulu.

## Le Service headless

`serviceName: db` désigne un Service **headless** (`clusterIP: None`) : au lieu d'une adresse virtuelle unique, il publie un nom DNS par pod, `db-0.db`. Les bases répliquées s'en servent pour se trouver entre elles.

!!Le serviceName d'un StatefulSet doit pointer vers un Service headless existant, sinon les noms DNS des pods n'existent pas!!

## Job et CronJob

Un **Job** lance des pods jusqu'à ce qu'ils réussissent une fois. Un **CronJob** crée un Job selon un horaire cron, comme une sauvegarde nocturne.

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup
spec:
  schedule: "0 3 * * *"
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 3600
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: dump
              image: postgres:16.4
              command: ["sh", "-c", "pg_dump -h db-0.db -U app app > /backup/app.sql"]
```

- `concurrencyPolicy: Forbid` : si la sauvegarde d'hier tourne encore, on n'en lance pas une deuxième.
- `backoffLimit` : nombre de nouvelles tentatives avant d'abandonner.
- `activeDeadlineSeconds` : durée maximale, un Job bloqué est tué.
- `restartPolicy` vaut `OnFailure` ou `Never` : jamais `Always` dans un Job.

!!Sans concurrencyPolicy: Forbid, une sauvegarde lente peut se chevaucher avec la suivante et saturer la base!!

## Labo réel (optionnel)

Avec **kind** installé (`kind create cluster`) :

```bash
kubectl apply -f db.yaml
kubectl get statefulset,pvc,pods
kubectl delete pod db-0        # le pod revient avec le même nom et le même disque
kubectl get pvc                 # data-db-0 est toujours là
kubectl create job --from=cronjob/backup backup-manuel
```

**À retenir :** `emptyDir` meurt avec le pod, PVC pour les données durables, StatefulSet pour des pods à identité stable et un disque chacun, `volumeClaimTemplates` et `volumeMounts` du même nom, Service headless, CronJob avec `concurrencyPolicy: Forbid`, `backoffLimit` et `activeDeadlineSeconds`.
