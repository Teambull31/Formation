# Ingress, montée en charge et mises à jour sans coupure

L'application tourne dans le cluster. Il reste à la rendre accessible depuis Internet, à suivre la charge, et à la mettre à jour sans qu'aucun utilisateur ne voie d'erreur.

## Le chemin d'une requête

Avant le YAML, le dessin. Chaque flèche est un objet de cette leçon, et chaque objet désigne le suivant **par son nom** :

```
Internet ──► Ingress « web »  (host app.example.test, chemin /)
                │  backend.service.name: web, port 80
                ▼
            Service « web »   (ClusterIP, port 80 → targetPort 8000)
                │  selector app: web
                ▼
            Pods app: web     (créés par le Deployment « web », port 8000)
                ▲
                │  scaleTargetRef.name: web
         HorizontalPodAutoscaler « web » (2 à 10 pods)
```

Un nom mal recopié casse la chaîne sans erreur visible : il faut relire chaque lien.

## Exposer : Service et Ingress

Un Service `ClusterIP` n'est joignable que depuis le cluster. Pour le Web, on place devant un **Ingress** : un routeur HTTP qui lit le nom de domaine et le chemin, termine le TLS, et envoie vers le bon Service. Il faut un **contrôleur d'Ingress** installé (ingress-nginx, Traefik) : le manifeste seul ne fait rien.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
spec:
  ingressClassName: nginx               # ← quel contrôleur traite cet Ingress
  tls:                                  # ← niveau 1 : HTTPS, à côté de rules
    - hosts: ["app.example.test"]       #   le même nom que dans rules
      secretName: web-tls               #   le certificat (Secret de type tls)
  rules:                                # ← niveau 1 : le routage
    - host: app.example.test            # une règle par nom de domaine
      http:
        paths:                          # une liste de chemins pour ce domaine
          - path: /
            pathType: Prefix            # « / » et tout ce qui commence par « / »
            backend:                    # aligné sur path : vers où envoyer CE chemin
              service:
                name: web               # ← le nom du Service
                port:
                  number: 80            # ← son port, pas celui du conteneur
```

`ingressClassName` choisit le contrôleur. Le certificat vit dans le Secret `web-tls`, souvent créé automatiquement par **cert-manager** avec Let's Encrypt.

Remarquez la profondeur : `backend` est à 12 espaces. Il appartient au chemin (`- path: /`), pas à la règle ni à l'Ingress. Un Ingress peut ainsi envoyer `/api` vers un Service et `/` vers un autre.

!!Un Service de type LoadBalancer par application crée un équilibreur payant chacun : un seul Ingress suffit pour tous les sites HTTP!!

## Mise à jour progressive : où placer la stratégie

Un Deployment remplace ses pods par vagues. Deux réglages pilotent la vague. La stratégie est une propriété **du Deployment**, pas du pod : elle se place sous le premier `spec`, à côté de `selector` et `template`. La sonde, elle, est une propriété **du conteneur**.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:                                  # ── niveau DEPLOYMENT ──
  # pas de « replicas » : l'HPA décide (voir plus bas)
  strategy:                            # ← ici, à côté de selector
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0                # jamais moins de pods prêts qu'avant
      maxSurge: 1                      # un pod de plus pendant la vague
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:                              # ── niveau POD ──
      containers:
        - name: web                    # ── niveau CONTENEUR ──
          image: registry.example.test/web:1.5.0
          ports:
            - containerPort: 8000
          resources:
            requests:
              cpu: 100m                # ← indispensable à l'HPA
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 256Mi
          readinessProbe:              # ← ici, dans le conteneur
            httpGet:
              path: /healthz
              port: 8000
```

`maxUnavailable: 0` : on ne retire jamais un ancien pod avant qu'un nouveau soit **prêt**. `maxSurge: 1` : on crée un pod de plus pendant la mise à jour. La notion de « prêt » vient de la **readinessProbe** : sans elle, Kubernetes envoie du trafic à un pod qui démarre encore.

```bash
kubectl rollout status deployment/web
kubectl rollout history deployment/web
kubectl rollout undo deployment/web
```

!!Sans readinessProbe, une mise à jour progressive envoie du trafic à des pods qui ne répondent pas encore : des erreurs 502 à chaque déploiement!!

## L'autoscaling horizontal

Le **HorizontalPodAutoscaler** (HPA) ajuste le nombre de réplicas selon une mesure, le plus souvent l'utilisation du CPU **par rapport à la demande** (`requests.cpu`).

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:                  # ← QUI ajuster : un objet désigné par type et nom
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70   # viser 70 % de requests.cpu en moyenne
```

- Sans `requests.cpu` sur le conteneur, le pourcentage n'a pas de base : l'HPA reste inactif.
- Il faut **metrics-server** dans le cluster.
- Quand un HPA gère le Deployment, retirez `spec.replicas` du manifeste : sinon chaque `kubectl apply` remet le nombre fixe et écrase la décision de l'HPA.

## Survivre à la maintenance : le PodDisruptionBudget

Quand un administrateur vide un nœud (`kubectl drain`) pour le mettre à jour, Kubernetes expulse ses pods. Un **PodDisruptionBudget** fixe un plancher :

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web
spec:
  minAvailable: 1
  selector:                 # ← comme un Deployment : avec matchLabels
    matchLabels:
      app: web
```

Le drain attend alors qu'un autre pod soit prêt avant d'expulser le dernier. Le sélecteur doit désigner les pods de l'application.

!!Un PodDisruptionBudget dont le sélecteur ne correspond à aucun pod ne protège rien, et Kubernetes ne signale aucune erreur!!

## Répartir les pods

Deux réplicas sur le même nœud tombent ensemble. `topologySpreadConstraints` (ou une `podAntiAffinity`) demande au planificateur de les répartir sur des nœuds ou des zones différents. Ce réglage est une propriété du **pod**, aligné sur `containers:`.

## Pas à pas : mettre l'application en production

1. Dans le Deployment, supprimez la ligne `replicas:`.
2. Sous le premier `spec:`, ajoutez le bloc `strategy:` avec `type: RollingUpdate`, `maxUnavailable: 0` et `maxSurge: 1`.
3. Dans le conteneur, ajoutez la `readinessProbe` HTTP sur le port 8000, et vérifiez que `requests.cpu` existe.
4. Passez le Service en `type: ClusterIP` (ou supprimez la ligne `type:`, c'est la valeur par défaut). Gardez `port: 80` et `targetPort: 8000`.
5. Après `---`, écrivez l'Ingress : `ingressClassName`, `tls`, puis `rules` avec host, chemin et `backend` vers `web:80`.
6. Après `---`, écrivez l'HPA avec `scaleTargetRef` vers le Deployment `web`, `minReplicas: 2`, `maxReplicas: 10`, CPU à 70.
7. Après `---`, écrivez le PodDisruptionBudget avec `minAvailable: 1` et le sélecteur `app: web`.
8. Validez avec `kubeconform -strict web.yaml`.

## Labo réel (optionnel)

```bash
kubectl apply -f web.yaml
kubectl get ingress,hpa,pdb
kubectl set image deployment/web web=registry.example.test/web:1.5.1
kubectl rollout status deployment/web
kubectl rollout undo deployment/web
```

**À retenir :** Ingress avec `ingressClassName`, hôte, chemin et TLS, `backend` sous le chemin ; `strategy` au niveau du Deployment, readinessProbe au niveau du conteneur, `maxUnavailable: 0` ; `rollout undo` pour revenir en arrière ; HPA sur `requests.cpu` et sans `spec.replicas` figé ; PodDisruptionBudget dont le sélecteur vise les pods.
