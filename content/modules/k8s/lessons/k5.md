# Ingress, montée en charge et mises à jour sans coupure

L'application tourne dans le cluster. Il reste à la rendre accessible depuis Internet, à suivre la charge, et à la mettre à jour sans qu'aucun utilisateur ne voie d'erreur.

## Exposer : Service et Ingress

Un Service `ClusterIP` n'est joignable que depuis le cluster. Pour le Web, on place devant un **Ingress** : un routeur HTTP qui lit le nom de domaine et le chemin, termine le TLS, et envoie vers le bon Service. Il faut un **contrôleur d'Ingress** installé (ingress-nginx, Traefik) : le manifeste seul ne fait rien.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
spec:
  ingressClassName: nginx
  tls:
    - hosts: ["app.example.test"]
      secretName: web-tls
  rules:
    - host: app.example.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web
                port:
                  number: 80
```

`ingressClassName` choisit le contrôleur. Le certificat vit dans le Secret `web-tls`, souvent créé automatiquement par **cert-manager** avec Let's Encrypt.

!!Un Service de type LoadBalancer par application crée un équilibreur payant chacun : un seul Ingress suffit pour tous les sites HTTP!!

## Mise à jour progressive

Un Deployment remplace ses pods par vagues. Deux réglages pilotent la vague :

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
```

`maxUnavailable: 0` : on ne retire jamais un ancien pod avant qu'un nouveau soit **prêt**. `maxSurge: 1` : on crée un pod de plus pendant la mise à jour. La notion de « prêt » vient de la **readinessProbe** : sans elle, Kubernetes envoie du trafic à un pod qui démarre encore.

```bash
kubectl rollout status deployment/web
kubectl rollout history deployment/web
kubectl rollout undo deployment/web
```

!!Sans readinessProbe, une mise à jour progressive envoie du trafic à des pods qui ne répondent pas encore : des erreurs 502 à chaque déploiement!!

## L'autoscaling horizontal

Le **HorizontalPodAutoscaler** (HPA) ajuste le nombre de réplicas selon une mesure, le plus souvent l'utilisation du CPU **par rapport à la demande** (`requests.cpu`).

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

- Sans `requests.cpu` sur le conteneur, le pourcentage n'a pas de base : l'HPA reste inactif.
- Il faut **metrics-server** dans le cluster.
- Quand un HPA gère le Deployment, retirez `spec.replicas` du manifeste : sinon chaque `kubectl apply` remet le nombre fixe et écrase la décision de l'HPA.

## Survivre à la maintenance : le PodDisruptionBudget

Quand un administrateur vide un nœud (`kubectl drain`) pour le mettre à jour, Kubernetes expulse ses pods. Un **PodDisruptionBudget** fixe un plancher :

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web
spec:
  minAvailable: 1
  selector:
    matchLabels:
      app: web
```

Le drain attend alors qu'un autre pod soit prêt avant d'expulser le dernier. Le sélecteur doit désigner les pods de l'application.

!!Un PodDisruptionBudget dont le sélecteur ne correspond à aucun pod ne protège rien, et Kubernetes ne signale aucune erreur!!

## Répartir les pods

Deux réplicas sur le même nœud tombent ensemble. `topologySpreadConstraints` (ou une `podAntiAffinity`) demande au planificateur de les répartir sur des nœuds ou des zones différents.

## Labo réel (optionnel)

```bash
kubectl apply -f web.yaml
kubectl get ingress,hpa,pdb
kubectl set image deployment/web web=registry.example.test/web:1.5.1
kubectl rollout status deployment/web
kubectl rollout undo deployment/web
```

**À retenir :** Ingress avec `ingressClassName`, hôte, chemin et TLS ; `maxUnavailable: 0` et readinessProbe pour zéro coupure ; `rollout undo` pour revenir en arrière ; HPA sur `requests.cpu` et sans `spec.replicas` figé ; PodDisruptionBudget dont le sélecteur vise les pods ; répartition sur plusieurs nœuds.
