# Planifier : cron et timers

Votre `tri.sh` marche. Reste à le faire tourner tout seul, sans y penser. C'est le rôle du planificateur.

## Les 5 champs de cron

Une ligne cron se lit ainsi : **minute, heure, jour du mois, mois, jour de la semaine**, puis la commande. L'étoile `*` veut dire « toutes les valeurs ». La ligne `15 12 * * 1-5` signifie : à 12 h 15, du lundi (1) au vendredi (5). On peut écrire une liste `1,2,3`, un intervalle `1-5` ou un pas `*/10`. On édite sa table avec `crontab -e`.

Décomposition d'une ligne, champ par champ :

```
15   12   *   *   1-5   /home/moi/tri.sh /home/moi/inbox >> /home/moi/tri.log 2>&1
│    │    │   │   │     └─ la commande, avec chemins absolus
│    │    │   │   └─ jour de la semaine : 1-5 = lundi à vendredi (0 et 7 = dimanche)
│    │    │   └─ mois : * = tous
│    │    └─ jour du mois : * = tous
│    └─ heure : 12
└─ minute : 15
```

Les cinq champs sont séparés par des espaces, toujours dans cet ordre. L'erreur classique est d'inverser minute et heure : `12 15 * * *` tourne à 15 h 12.

| Ligne | Sens |
| --- | --- |
| `0 * * * *` | au début de chaque heure |
| `*/10 * * * *` | toutes les 10 minutes |
| `30 2 * * 0` | le dimanche à 2 h 30 |
| `0 9 1 * *` | le 1er de chaque mois à 9 h |

## Cron n'est pas votre terminal

C'est là que tout casse. Cron lance la commande sans votre environnement.

!!Cron ne démarre pas dans votre dossier : un chemin relatif ne trouve rien!!

Écrivez donc des **chemins absolus** pour le script, ses fichiers et son log. Le `PATH` de cron est **minimal** (souvent `/usr/bin:/bin`) : une commande installée ailleurs sera introuvable.

!!Dans une crontab, un % non protégé coupe la commande : écrivez \% (par exemple pour date +\%F)!!

## Garder une trace

Cron n'affiche rien à l'écran. Sans log, vous ne saurez jamais pourquoi la tâche a échoué.

```
15 12 * * 1-5 /home/moi/tri.sh /home/moi/inbox >> /home/moi/tri.log 2>&1
```

**`>>` ajoute** à la fin du fichier. `2>&1` envoie aussi les erreurs dans le même fichier, et il se place **après** le nom du log.

!!Un seul > écrase le log à chaque passage : vous perdez l'historique!!

## Les timers systemd

Sous Linux moderne, l'alternative est le **timer systemd en mode utilisateur** : un fichier `.service` (ce qu'on lance) et un fichier `.timer` (quand). On l'active avec `systemctl --user enable --now tri.timer`. Les logs se lisent avec `journalctl --user`. Le « quand » s'écrit `OnCalendar=Mon..Fri 12:15`. Avantage : l'historique est intégré et on rattrape les passages manqués avec `Persistent=true`. Pour qu'un timer utilisateur tourne sans session ouverte, lancez `loginctl enable-linger`.

Les deux fichiers, complets. Ils vont dans `~/.config/systemd/user/`, et portent le **même nom** avant l'extension : c'est ce qui relie le timer à son service.

```ini
# Fichier : ~/.config/systemd/user/tri.service : CE QU'ON LANCE
[Unit]
Description=Ranger le dossier inbox

[Service]
Type=oneshot                                      # une exécution qui se termine, pas un démon
ExecStart=/home/moi/tri.sh /home/moi/inbox        # chemins absolus, comme en cron
```

```ini
# Fichier : ~/.config/systemd/user/tri.timer : QUAND
[Unit]
Description=Ranger inbox en semaine à 12 h 15

[Timer]
OnCalendar=Mon..Fri 12:15                         # jours puis heure
Persistent=true                                   # rattrape le passage manqué si la machine était éteinte

[Install]
WantedBy=timers.target                            # nécessaire pour « enable »
```

Chaque fichier est découpé en **sections** entre crochets. Une clé n'a de sens que dans sa section : `OnCalendar` dans `[Timer]`, `ExecStart` dans `[Service]`. Placée ailleurs, elle est ignorée avec un simple avertissement dans le journal.

Pas de redirection `>> log 2>&1` ici : systemd capture la sortie lui-même. On la lit avec `journalctl --user -u tri.service`.

## Idempotence

Une tâche planifiée peut tourner deux fois, ou être relancée après une panne. Elle doit donc être **idempotente** : la relancer ne change rien de plus. Votre `tri.sh` l'est, car il ne touche pas ce qui est déjà rangé.

!!Un script qui ajoute des lignes ou renomme à chaque passage s'emballe en production!!

## Pas à pas : planifier tri.sh

1. Dans le dossier du TP, notez le chemin absolu : `pwd`.
2. Vérifiez que le script est exécutable : `ls -l tri.sh` doit montrer un `x`, sinon `chmod +x tri.sh`.
3. Testez la commande exacte à la main, avec les chemins absolus et la redirection, puis lisez le log.
4. Écrivez `planning.cron` : `15 12 * * 1-5`, une espace, puis cette commande, sans rien après `2>&1`.
5. Pour l'installer pour de vrai : `crontab planning.cron`, puis `crontab -l` pour relire.
6. Pour tester sans attendre midi, mettez temporairement `* * * * *`, attendez une minute, lisez le log, puis remettez l'horaire.

**À retenir :** 5 champs, chemins absolus, log avec `>> … 2>&1`, et un script qu'on peut relancer sans risque.
