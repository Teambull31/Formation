# Mises à jour OTA : changer le micrologiciel à distance, sans rien casser

**Le problème concret :** votre contrôleur de piscine est dans un local technique, la pompe est branchée dessus, et vous venez de corriger un bogue. Aller chercher la carte, brancher un câble USB, reflasher : on ne le fera pas pour dix cartes, ni pour la carte d'un client. Il faut pouvoir **envoyer le nouveau micrologiciel par le réseau** : c'est l'**OTA** (*Over-The-Air*, mise à jour « par les airs »). Mais une mise à jour est le moment le plus dangereux de la vie d'une carte : si elle est mal faite, la carte devient **inutilisable à distance** (briquée), ou pire, elle **installe le programme d'un inconnu**. Cette leçon apprend à la faire bien : **deux emplacements** pour le programme, un téléchargement **vérifié** (`esp_https_ota`), une **comparaison de versions** correcte, la gestion des **échecs** (image corrompue, connexion coupée), le **relais en état sûr** pendant l'opération, et un **redémarrage seulement après un succès**.

Cette leçon contient toute la théorie du TP. Lisez-la dans l'ordre : les messages du contrôle vous disent quelle section relire. Elle suppose la leçon précédente (MQTT sur TLS, certificat du courtier, identifiants en NVS, relais éteint quand la liaison est perdue), les commandes MQTT du TP 8 et la **limite de sécurité de 80 %** du TP 6.

Tout ce qui est écrit ici est le vrai ESP-IDF (version 5.5.3), sauf la section « Ce que le simulateur simplifie », qui liste les écarts du TP. La **validation après le redémarrage** (confirmer que la nouvelle version marche, ou revenir à l'ancienne) est le sujet de la leçon suivante : ici on s'arrête au redémarrage.

## Deux slots et la table de partitions

Un programme **ne peut pas s'écraser lui-même** : pendant qu'il s'exécute, il est lu dans la mémoire flash, et une coupure de courant au milieu de l'écriture laisserait un programme à moitié écrit, donc une carte qui ne démarre plus. La solution d'ESP-IDF : **deux emplacements** (*slots*) pour le programme. La carte tourne dans l'un ; la mise à jour s'écrit dans **l'autre** ; et ce n'est qu'une fois l'image écrite et vérifiée qu'on dit au démarrage d'utiliser l'autre. Tant que ce dernier geste n'est pas fait, la carte redémarrerait sur l'ancien programme, intact.

Les emplacements sont décrits par la **table de partitions**, un tableau gravé dans la flash qui découpe la mémoire en zones nommées. Voici la table « application d'usine, deux OTA » de la documentation d'ESP-IDF (menu `CONFIG_PARTITION_TABLE_TYPE`, choix « Factory app, two OTA definitions »), qui tient dans une flash de 4 Mo :

```
# Name,   Type, SubType, Offset,   Size
nvs,      data, nvs,     0x9000,   0x4000
otadata,  data, ota,     0xd000,   0x2000
phy_init, data, phy,     0xf000,   0x1000
factory,  app,  factory, 0x10000,  1M
ota_0,    app,  ota_0,   0x110000, 1M
ota_1,    app,  ota_1,   0x210000, 1M
```

- **`ota_0` et `ota_1`** (type `app`) : les deux emplacements du programme. Chacun doit contenir le programme **entier**, avec une taille suffisante (1 Mo ici) ; le début d'une partition d'application est aligné sur 64 Ko (0x10000).
- **`otadata`** (type `data`, sous-type `ota`) : deux secteurs de flash (0x2000 octets) qui disent **quel emplacement le démarrage doit lancer**. Les deux secteurs portent les mêmes données et un compteur qui désigne le plus récent. La mise à jour n'écrit `otadata` **qu'à la fin**, une fois l'image vérifiée : c'est ce qui rend l'opération sûre.
- **`factory`** : le programme d'usine, lancé tant que `otadata` est vide (effacé à 0xFF). Une table sans `factory` est possible : le démarrage lance alors le premier emplacement OTA. Le TP utilise deux emplacements seuls.
- **`nvs`** : la mémoire clé/valeur du TP 9 (et vos identifiants du TP 10). Elle n'est pas touchée par une mise à jour d'application : vos données survivent.

Le **bootloader** (le petit programme qui s'exécute avant le vôtre) lit `otadata`, choisit l'emplacement et le lance. Quand la mise à jour d'une application est interrompue (coupure de courant en plein téléchargement), le programme en cours **reste en place** : la documentation d'ESP-IDF appelle cela le mode sûr pour les applications. Les autres zones (bootloader, table de partitions, NVS...) se mettent à jour en mode non sûr : ce n'est pas notre sujet.

Quelle partition est visée par la mise à jour ? « L'autre » : `esp_ota_get_next_update_partition` choisit l'emplacement suivant dans l'ordre, jamais celui qui tourne. Vous n'avez pas à l'appeler avec `esp_https_ota`, qui le fait elle-même.

## esp_https_ota : mettre à jour en une fonction

`esp_https_ota` télécharge une image par HTTPS, l'écrit dans l'emplacement libre, la vérifie, et, si tout va bien, **fait de cet emplacement le prochain emplacement de démarrage**. Elle se configure avec deux structures : la configuration du client HTTP (`esp_http_client_config_t`, qui porte l'adresse et le certificat) et la configuration de l'OTA (`esp_https_ota_config_t`, qui pointe sur la première) :

```cpp
esp_http_client_config_t http = {};
http.url = "https://broker.local:8443/firmware/pool-ctl-1.10.0.bin";
http.cert_pem = _binary_server_cert_pem_start;   // le certificat du serveur (section suivante)

esp_https_ota_config_t cfg = {};
cfg.http_config = &http;

esp_err_t err = esp_https_ota(&cfg);             // BLOQUE jusqu'à la fin du téléchargement
if (err == ESP_OK) {
    esp_restart();                               // et seulement dans ce cas
}
```

La fonction **bloque** celui qui l'appelle pendant tout le téléchargement (de quelques secondes à plusieurs minutes pour une image de 1 Mo sur un Wi-Fi domestique), et **ne redémarre pas la carte** : la documentation dit que si elle renvoie `ESP_OK`, **`esp_restart()` doit être appelé** pour démarrer sur la nouvelle image. C'est exactement ce que fait l'exemple officiel `simple_ota_example` : il construit la configuration (adresse, certificat), appelle `esp_https_ota`, et, si le résultat est `ESP_OK`, journalise puis appelle `esp_restart()` ; sinon il journalise « Firmware upgrade failed » et ne redémarre pas. Il exécute cela dans une **tâche à lui** : le téléchargement TLS a besoin d'une pile plus grande que ce qu'on veut donner à `app_main`.

**La forme détaillée.** ESP-IDF propose aussi le même travail en plusieurs appels : `esp_https_ota_begin` (ouvre la connexion), `esp_https_ota_get_img_desc` (lit l'en-tête de l'image, **dont sa version**, avant d'en télécharger le reste), puis `esp_https_ota_perform` appelée en boucle tant qu'elle renvoie `ESP_ERR_HTTPS_OTA_IN_PROGRESS` (on peut y afficher une progression), `esp_https_ota_is_complete_data_received` (l'image est-elle complète ?) et `esp_https_ota_finish` (vérifie, bascule l'emplacement de démarrage), ou `esp_https_ota_abort` pour tout nettoyer après une erreur. C'est le schéma de l'exemple officiel `advanced_https_ota`. Le simulateur du TP **ne fournit pas** cette forme : le TP utilise la forme simple.

## Vérifier le serveur, et jamais en clair

Une mise à jour est le **pouvoir absolu** sur la carte : qui contrôle l'image contrôle la pompe. Le téléchargement doit donc se faire avec la même exigence que MQTT au TP 10 : **chiffré** et **avec la vérification du certificat du serveur** (chaîne, dates, nom).

- **`cert_pem`** : le certificat à croire, en PEM terminé par un NUL, comme `broker.verification.certificate` en MQTT. La documentation d'`esp_https_ota` recommande d'y mettre le certificat **racine** plutôt qu'un intermédiaire, parce que la racine a la plus longue validité. C'est ce que fait le TP : `http.cert_pem = _binary_server_cert_pem_start;` (le symbole du TP 10).
- **`crt_bundle_attach = esp_crt_bundle_attach`** : le paquet des autorités publiques, pour un serveur public (un site connu, avec un certificat d'une autorité connue). Le serveur **privé** du TP n'y figure pas : avec le paquet seul, la poignée de main échoue et `esp_https_ota` renvoie `ESP_ERR_HTTP_CONNECT`.
- **`use_global_ca_store`** : le magasin global de certificats du programme.
- **Aucune des trois** : `esp_https_ota` refuse avant de se connecter, avec `ESP_ERR_INVALID_ARG` et le message « No option for server verification is enabled in esp_http_client config ». (Une option de configuration, `CONFIG_ESP_HTTPS_OTA_ALLOW_HTTP`, lève ce refus : elle est réservée aux essais, et ne doit jamais être activée dans un programme livré.)
- **`skip_cert_common_name_check`** : comme au TP 10, ne l'écrivez pas. L'exemple officiel ne la positionne que sous une option de test (`CONFIG_EXAMPLE_SKIP_COMMON_NAME_CHECK`).

**Le piège de `http://`.** La fonction **ne regarde jamais le début de l'adresse**. Avec une adresse `http://...`, le client HTTP télécharge **en clair**, sans poignée de main TLS, et le `cert_pem` que vous avez donné est **ignoré** : la fonction ne proteste pas (tant qu'une option de vérification est donnée, elle est satisfaite). Une adresse reçue sur le réseau, qu'on ne contrôle pas, peut donc faire télécharger une image en clair, que n'importe quel appareil du Wi-Fi peut remplacer au passage. **C'est à votre programme de refuser** toute adresse qui ne commence pas par `https://`, **avant** d'appeler `esp_https_ota`. Le TP le vérifie : le simulateur écrit dans la trace si le téléchargement s'est fait en clair.

Deux idées complémentaires. D'abord, TLS garantit **à qui** on parle, pas **ce que contient** l'image : une image fabriquée par un attaquant qui contrôle le serveur passe TLS sans difficulté (voir la section sur la signature). Ensuite, la commande `{"ota": "<adresse>"}` laisse ici l'adresse du **serveur** au choix de l'expéditeur, ce qui est commode pour le TP mais trop large pour un produit : dans un vrai programme, l'adresse du serveur est une constante, et la commande ne porte que la **version** voulue.

## Comparer les versions

Quand on reçoit l'ordre de mettre à jour, la première question est : **cette image est-elle vraiment plus récente ?** Installer la même version est un travail inutile (et une usure de la flash), installer une version **plus ancienne** est une régression, parfois une faille qu'on avait corrigée qui revient. La règle du TP : **seulement vers une version strictement plus récente**.

**Où lire la version courante.** Chaque image contient une **description** (`esp_app_desc_t`) dont le champ `version` est un texte de 31 caractères au plus, fixé à la compilation (variable `PROJECT_VER` du projet, ou le résultat de `git describe`). Le programme en cours la lit :

```cpp
#include "esp_app_desc.h"
const char *courante = esp_app_get_description()->version;   // par exemple "1.9.0"
```

**Où lire la version proposée.** Avec la forme détaillée, on lit l'en-tête de l'image **avant** de la télécharger (`esp_https_ota_get_img_desc`) et on abandonne si la version ne convient pas : c'est ce que fait l'exemple `advanced_https_ota` (il ne refuse d'ailleurs que la version **identique**, par `memcmp` : « strictement plus récente » est votre règle, pas celle de l'exemple). Avec la forme simple, on ne sait rien de l'image avant de l'avoir installée. Le TP prend donc la version **dans le nom du fichier de l'adresse** : `.../pool-ctl-1.10.0.bin` annonce la version `1.10.0` (la fonction fournie `version_depuis_url` l'extrait). Beaucoup de serveurs de mise à jour nomment ainsi leurs fichiers, ou publient à côté un petit fichier qui liste les versions. Cette version est une **annonce** : seul l'en-tête de l'image dit la vérité, d'où l'intérêt de la forme détaillée dans un vrai produit.

**Comparer deux versions `x.y.z`.** Une version est trois **nombres** séparés par des points (majeur, mineur, correctif). On les compare **un par un, de gauche à droite, comme des nombres** :

1. lire `x`, `y`, `z` de chaque version ;
2. si les `x` diffèrent, le plus grand gagne ; sinon on passe aux `y` ; sinon aux `z` ;
3. si les trois sont égaux, les versions sont **identiques** : ce n'est pas « plus récent ».

!!Ne comparez jamais deux versions comme des **textes** (`strcmp`) : `"1.10.0"` est classée avant `"1.9.0"`, alors que la version 1.10.0 est la plus récente. Un contrôle qui compare des textes refuse la bonne mise à jour et accepterait la mauvaise!!

Pour lire les trois nombres : `sscanf(texte, "%d.%d.%d%c", &x, &y, &z, &reste)` renvoie le **nombre de champs lus** ; s'il renvoie exactement **3**, le texte est de la forme voulue et il n'y a rien après (si un caractère traîne, comme dans `1.2.3a`, le quatrième champ est lu et le résultat vaut 4). Avec `strtol`, on avance dans le texte avec le pointeur de fin qu'elle rend, et on vérifie à chaque étape qu'on trouve bien un point puis un chiffre. **Une version qui n'a pas la forme `x.y.z`** (`1.2`, `abc`, un nombre négatif) **n'est jamais « plus récente »** : le TP la refuse. Les versions avec suffixe (`1.2.3-beta`) existent (la norme « semver ») mais sortent du TP.

**Ce que le démarrage ne fait pas.** Le bootloader ne compare **pas** ces textes : il n'a aucune règle sur les versions, c'est la **politique de votre application**. (ESP-IDF a une protection distincte contre le retour en arrière, l'*anti-rollback*, fondée sur un numéro de version de sécurité gravé dans les fusibles de la puce : elle sort du TP.)

## Valider l'image : signature et erreurs

Avant d'adopter l'image, ESP-IDF la **valide** : l'en-tête (marqueur d'image), la somme de contrôle de l'image, et, si les options de sécurité sont activées, sa **signature**. Cette validation a lieu à la fin du téléchargement (la puce visée par l'image, elle, est contrôlée dès la lecture de l'en-tête, avec une erreur à part, `ESP_ERR_INVALID_VERSION`), et une image qui échoue ne devient **jamais** l'image de démarrage : elle fait renvoyer **`ESP_ERR_OTA_VALIDATE_FAILED`**. L'application continue sur l'ancienne image, sans autre dégât.

**La signature.** Une somme de contrôle détecte une image abîmée, pas une image **fabriquée**. La **signature** de l'application répond à « qui l'a construite ? » : on signe l'image avec une clé privée (gardée chez le fabricant), la carte vérifie avec la clé publique correspondante. ESP-IDF le fait de deux façons : avec le **démarrage sécurisé** (*secure boot*) de la puce, ou, **sans lui**, par une vérification des mises à jour signées (options `CONFIG_SECURE_SIGNED_APPS_NO_SECURE_BOOT` et `CONFIG_SECURE_SIGNED_ON_UPDATE_NO_SECURE_BOOT`). Quand une signature est exigée, une image mal signée fait renvoyer `ESP_ERR_OTA_VALIDATE_FAILED`. TLS protège **le chemin** (on parle bien à notre serveur), la signature protège **l'image** (même un serveur piraté ne peut pas faire installer un programme qu'il a fabriqué) : les deux se complètent.

**Les erreurs que `esp_https_ota` renvoie** (celles que le TP rencontre ; ne comptez pas sur d'autres) :

- `ESP_OK` : l'image est installée et l'emplacement de démarrage est basculé. Il faut redémarrer pour l'utiliser ;
- `ESP_ERR_INVALID_ARG` : configuration refusée avant toute connexion (aucune option de vérification, pas d'adresse...) ;
- `ESP_ERR_HTTP_CONNECT` : la connexion n'a pas pu s'ouvrir (Wi-Fi sans adresse IP, serveur injoignable, **poignée de main TLS qui échoue**, par exemple un certificat qui n'est pas celui du serveur) ;
- `ESP_FAIL` : le serveur ne connaît pas l'adresse (erreur 404), ou la **connexion est coupée** avant la fin de l'image (« Connection closed before complete data was received ») ;
- `ESP_ERR_OTA_VALIDATE_FAILED` : l'image téléchargée est invalide (corrompue, mal signée) ;
- `ESP_ERR_OTA_ROLLBACK_INVALID_STATE` : la carte tourne sur une image qui n'a pas encore été confirmée (voir la leçon suivante) : la mise à jour est impossible tant qu'elle ne l'est pas.

Ne vous appuyez pas sur le **code exact** dans votre logique : testez `err == ESP_OK` ; pour tout le reste, **journalisez le nom du code** (`esp_err_to_name(err)`), c'est ce qui permet de comprendre un échec à distance. Le contrôle du TP exige le nom du code dans le message d'échec.

## Un échec ne doit rien casser

Une mise à jour peut échouer pour des raisons banales : le Wi-Fi coupe en plein téléchargement, le serveur envoie une image corrompue, la carte n'a plus de mémoire. La règle : **un échec ne coûte rien**. Le programme en cours continue de tourner (c'est la garantie des deux emplacements), et votre code doit :

1. **tester le résultat** de `esp_https_ota` : jamais dans `ESP_ERROR_CHECK`, qui **arrête la carte** (elle redémarrerait en boucle devant une image corrompue que le serveur renvoie à chaque tentative) ;
2. **journaliser l'échec** : `ESP_LOGE(TAG, "mise à jour échouée : %s", esp_err_to_name(err));`. Le format que le contrôle exige : un message de **niveau E** (ou W), de **tag `ota`**, qui contient le **nom du code d'erreur** ;
3. **ne pas redémarrer** : pas de `esp_restart()` après un échec ;
4. **ne pas réessayer en boucle** : une commande = une tentative ;
5. laisser le **service continuer** (télémétrie, commandes).

**Le relais pendant la mise à jour.** Pendant le téléchargement, la carte est occupée (`esp_https_ota` bloque), et elle peut redémarrer à tout moment à la fin : une pompe qui tourne **sans personne pour la surveiller** est un danger. La règle de sécurité du TP, dans la logique du TP 10 : **juste avant `esp_https_ota`, éteindre le relais** (`regler_relais(false)`) ; **pendant** la mise à jour, **aucune commande** `{"relay": true}` ne l'allume (le code fourni refuse ces commandes tant qu'une mise à jour est demandée ou en cours) ; **après un échec**, il **reste éteint** tant qu'une nouvelle commande ne l'a pas allumé (on ne rallume pas de soi-même « pour rendre service » : comme au TP 10, rien ne se rallume tout seul).

Mais **la décision vient avant**. Une demande **refusée** (version identique, adresse en `http://`) ne démarre aucune mise à jour : la pompe n'a aucune raison de s'arrêter. Le contrôle vérifie donc aussi que, dans ce cas, **le relais n'est pas touché**. L'ordre est : 1. vérifier l'adresse, 2. vérifier la version, 3. **seulement alors** éteindre le relais et télécharger.

**Journaliser un refus.** Un refus n'est pas une erreur du programme, mais l'opérateur doit pouvoir le lire : `ESP_LOGW(TAG, "mise à jour refusée : version proposée %s, version courante %s", ...)`. Le format exigé : un message de **niveau W** (ou E), de **tag `ota`**, qui contient, pour un refus de version, **la version proposée et la version courante**, et, pour un refus d'adresse, **l'adresse refusée**.

## Quand redémarrer, et ce qui suit

La règle est brève : **on redémarre une seule fois, après un `ESP_OK`, et jamais autrement**. `esp_restart()` est le seul moyen d'utiliser la nouvelle image : tant qu'on ne redémarre pas, la carte continue sur l'ancienne, bien que l'emplacement de démarrage soit déjà basculé. Redémarrer **malgré** un échec n'apporte rien (l'emplacement de démarrage n'a pas changé : la carte repartirait sur le même programme) et coupe le service pour rien, la liaison MQTT comprise.

Avant `esp_restart()`, le programme ne doit plus rien laisser en route : le relais est déjà éteint (il l'est depuis le début de la mise à jour), et le redémarrage se fait sans tarder (le contrôle accorde 10 s entre la fin de la mise à jour et le redémarrage). Après le redémarrage, le programme redémarre **depuis `app_main`** : la NVS est conservée, le Wi-Fi et MQTT se reconnectent, le relais repart **éteint**, et rien ne l'allume avant la prochaine commande. Le programme fourni annonce sa version au démarrage (`ESP_LOGI(TAG, "démarrage, version %s", ...)`) : c'est ce que le contrôle lit pour s'assurer que la nouvelle version tourne.

**Ce qui arrive ensuite (la leçon suivante).** Quand le bootloader est compilé avec le retour arrière activé (`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`, désactivé par défaut dans ESP-IDF, activé dans le simulateur), la nouvelle image démarre dans un état **« à confirmer »** (`ESP_OTA_IMG_PENDING_VERIFY`) : le programme est censé se tester puis appeler `esp_ota_mark_app_valid_cancel_rollback()` ; si la carte redémarre **avant** cette confirmation, le bootloader abandonne la nouvelle image et relance l'ancienne. **Le programme de ce TP ne confirme rien** : il s'arrête au redémarrage, et le TP ne provoque aucun second redémarrage. C'est un choix de leçon, pas une bonne pratique à livrer : un programme réel avec ce retour arrière activé doit confirmer sa nouvelle image, ce que la leçon suivante apprend à faire. Cette confirmation est aussi la raison pour laquelle une mise à jour est refusée (`ESP_ERR_OTA_ROLLBACK_INVALID_STATE`) tant que la précédente n'est pas confirmée.

## Ne pas bloquer le gestionnaire MQTT

La commande `{"ota": "<adresse>"}` arrive dans le **gestionnaire d'événements MQTT**, qui s'exécute dans la tâche `mqtt_task`. Cette tâche ne doit **jamais attendre** (leçon précédente) : or le téléchargement dure des secondes, voire des minutes. Si on le fait dans le gestionnaire, plus aucun message n'est traité pendant ce temps, le client MQTT ne répond plus au courtier (et est déconnecté), et on ne peut plus rien arrêter. Même schéma que pour la perte de liaison au TP 10 :

1. le gestionnaire **extrait l'adresse** de la commande, la **copie** dans un tampon et **lève un drapeau** (`xEventGroupSetBits(groupe_liaison, BIT_OTA)`) ;
2. la boucle d'`app_main`, qui attend ces drapeaux (`xEventGroupWaitBits` avec un délai), voit `BIT_OTA` et **fait** la mise à jour (`mettre_a_jour`), avec une copie de l'adresse.

Le TP fournit `url_dans_commande`, qui extrait l'adresse, la copie dans `url_ota` et empêche deux demandes simultanées (`ota_demandee`) ; vous écrivez le geste du gestionnaire : si elle renvoie `true`, **lever `BIT_OTA`**. Dans un programme réel, le téléchargement se ferait plutôt dans une **tâche dédiée** à l'OTA (créée quand on la demande), avec une pile de plusieurs kilo-octets : c'est ce que fait l'exemple officiel. Le TP fait le téléchargement dans `app_main`, ce qui évite une tâche de plus : le simulateur ne limite pas la pile.

## Le programme du TP en un coup d'œil

`main.cpp` est fourni avec tout le client du TP 10 (Wi-Fi, NVS, relais GPIO 5, capteur, télémétrie, commandes du TP 8, identifiants lus en NVS, `mqtts://` avec vérification, attente croissante) et l'extraction de l'adresse et de la version. Il reste **trois fonctions**, marquées `TODO étape N` :

1. **`version_plus_recente(nouvelle, courante)`** : `true` seulement si `nouvelle` est strictement plus récente que `courante` (comparaison numérique `x.y.z`, `false` si l'une des deux a une autre forme).
2. **Le gestionnaire MQTT**, branche `MQTT_EVENT_DATA` : si `url_dans_commande(ev->data, ev->data_len)` renvoie `true`, lever `BIT_OTA`.
3. **`mettre_a_jour(url)`**, appelée par `app_main` (jamais par le gestionnaire), dans cet ordre :
   1. adresse qui ne commence pas par `https://` : `ESP_LOGW` de refus qui contient l'adresse, puis retour ;
   2. version proposée (`version_depuis_url`) pas strictement plus récente que `esp_app_get_description()->version` : `ESP_LOGW` de refus qui contient les deux versions, puis retour ;
   3. `regler_relais(false)` ;
   4. `esp_http_client_config_t` (`url`, `cert_pem = _binary_server_cert_pem_start`), `esp_https_ota_config_t` (`http_config`), `esp_err_t err = esp_https_ota(&cfg)` ;
   5. `err != ESP_OK` : `ESP_LOGE` qui contient `esp_err_to_name(err)`, puis retour (aucun redémarrage) ;
   6. sinon : `ESP_LOGI` de succès, puis `esp_restart()`.

`app_main` (fourni) : initialise le relais, l'ADC, la NVS, connecte le Wi-Fi, annonce la version courante, démarre MQTT, puis boucle : attente des drapeaux `BIT_PERDU` (liaison perdue : `reagir_a_la_perte`) et `BIT_OTA` (mise à jour : `mettre_a_jour` avec une copie de l'adresse), et une télémétrie tous les 10 tours.

Les **sept exécutions** du contrôle (niveau 72,5 %, `{"relay": true}` à 20 s, `{"ota": adresse}` à 40 s, de nouveau `{"relay": true}` à 41 s) : **a** version 1.9.0, image 1.10.0 valide : mise à jour puis redémarrage (c'est la version 1.10.0 qui annonce son démarrage) ; **b** version 1.4.2, image 2.0.0 corrompue : échec journalisé, pas de redémarrage ; **c** version identique : refus, aucun téléchargement ; **d** version 1.0.0, image 1.0.1 coupée à 60 % : échec journalisé, pas de redémarrage ; **e** version plus ancienne (1.9.9 contre 1.10.0 : deux textes qui se comparent à l'envers) : refus ; **f** adresse en `http://` : refus ; **g** version `1.2.3a` (qui n'a pas exactement la forme `x.y.z`) : refus. Les versions de b et de d ne diffèrent que par certains nombres (2.0.0 contre 1.4.2 : le mineur baisse mais le majeur monte ; 1.0.1 contre 1.0.0 : seul le correctif change) : une comparaison qui ne regarde pas tous les nombres, ou qui exige que chacun soit au moins égal, s'y trompe.

## Ce que le simulateur simplifie

Le simulateur fournit `esp_https_ota` (forme simple), l'emplacement qui tourne, la version et l'état de chaque emplacement. Ce qu'il fait, et ce qu'il ne fait pas :

- **Pas d'octets d'image.** Le « serveur de micrologiciels » est décrit par le scénario : une liste d'adresses exactes, chacune avec une version, un indicateur « valide » (image qui se télécharge entière mais échoue à la validation : somme de contrôle, signature...) et un instant de coupure en pourcentage. Une adresse inconnue donne `ESP_FAIL` (comme une erreur 404). **La signature n'est pas simulée** : l'indicateur « valide » en tient lieu.
- **La version vient de l'adresse dans le programme du TP** : le simulateur, lui, installe la version décrite par le scénario. Il n'a ni `esp_https_ota_begin`, ni `esp_https_ota_get_img_desc`, ni `esp_https_ota_perform`, ni `esp_https_ota_finish`, ni `esp_ota_begin/write/end` ni `esp_ota_set_boot_partition` : la forme détaillée de la leçon n'est pas disponible.
- **La poignée de main TLS** est simulée comme au TP 10 (le certificat que vous donnez est comparé à celui du serveur que le pilote fabrique à chaque exécution ; le paquet de certificats public refuse le serveur du TP). Le serveur de micrologiciels est le même hôte que le courtier (`broker.local`), donc le même certificat.
- **Une adresse `http://` n'est pas refusée** par le simulateur, pas plus que par ESP-IDF : le téléchargement se fait en clair, et la trace le dit (`cleartext`). C'est le contrôle du TP qui l'exige du programme.
- **Le temps** : le téléchargement bloque l'appelant 100 ms (connexion) puis 20 ms par pour cent de l'image, soit 2,1 s en tout, en temps virtuel ; les autres tâches continuent.
- **Un échec détruit l'ancienne image de l'autre emplacement, sur une vraie carte comme dans le simulateur.** La mise à jour s'écrit dans l'autre emplacement : `esp_https_ota` appelle `esp_ota_begin` avec l'écriture séquentielle, qui efface chaque secteur avant d'y écrire, en commençant par l'en-tête (avec `bulk_flash_erase`, tout l'emplacement est effacé d'un coup). Après une coupure ou une image invalide, il n'y a donc **plus d'ancienne image vers laquelle revenir** (`esp_ota_check_rollback_is_possible` renvoie faux) ; l'application en cours, elle, continue de tourner et reste l'image de démarrage. La seule simplification du simulateur est le **moment** : il efface tout l'emplacement dès le début du téléchargement, une vraie carte l'efface au fil de l'écriture.
- **Pas de pile limitée** : le simulateur ne dit rien de la taille de la pile nécessaire au téléchargement TLS, ni de la mémoire.
- **Le retour arrière est activé** dans le simulateur (`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`). Le TP ne l'exerce pas (un seul redémarrage, après la mise à jour).
- **Les versions** : 31 caractères au plus. Les versions et les états des deux emplacements **survivent aux redémarrages** (la flash survit), comme la NVS.

## Pièges

!!N'appelez jamais `esp_https_ota` dans `ESP_ERROR_CHECK` : une image corrompue ou une connexion coupée est un cas normal, qui ne doit pas arrêter la carte; testez le code renvoyé et journalisez son nom!!

!!Ne redémarrez jamais après un échec, ni avant la fin d'une mise à jour réussie : on appelle `esp_restart()` seulement quand `esp_https_ota` a renvoyé `ESP_OK`!!

!!Ne comparez pas les versions comme des textes (`strcmp`) : « 1.10.0 » est classée avant « 1.9.0 » ; comparez les nombres `x`, `y`, `z` un par un, et refusez la version identique ou plus ancienne!!

!!Ne téléchargez jamais une image en clair et ne coupez jamais la vérification du serveur : refusez toute adresse qui n'est pas en `https://`, donnez `cert_pem`, et n'écrivez ni `skip_cert_common_name_check` ni une option qui la contourne!!

!!N'éteignez pas le relais pour une demande refusée, et ne le laissez pas allumé (ni ne le rallumez de vous-même) pendant ou après une vraie mise à jour : décidez d'abord, éteignez ensuite, et ne rallumez que sur une nouvelle commande!!

!!Ne faites pas le téléchargement dans le gestionnaire MQTT : il lève un drapeau, et c'est `app_main` (ou une tâche dédiée) qui met à jour!!

## À retenir

- **Deux emplacements** (`ota_0`, `ota_1`) et `otadata` : la mise à jour s'écrit dans l'emplacement libre et `otadata` ne change qu'une fois l'image vérifiée ; une coupure laisse l'ancien programme en place.
- **`esp_https_ota`** (forme simple) : une configuration HTTP (`url`, `cert_pem`) dans une configuration OTA, un appel **bloquant** ; `ESP_OK` veut dire « image installée, redémarrez ». La forme détaillée (`begin`, `get_img_desc`, `perform`, `finish`) lit la version avant de télécharger.
- **Le serveur est vérifié** (`cert_pem`, ou le paquet public pour un serveur public) ; sans aucune option, `ESP_ERR_INVALID_ARG`. **`http://` n'est pas refusé** par la fonction : c'est à vous de n'accepter que `https://`.
- **Versions** : comparer `x`, `y`, `z` comme des **nombres**, jamais comme des textes ; seulement vers une version **strictement plus récente** ; une forme invalide est refusée.
- **Validation et signature** : une image invalide donne `ESP_ERR_OTA_VALIDATE_FAILED` ; la signature (démarrage sécurisé, ou mises à jour signées sans lui) protège l'image, TLS protège le chemin.
- **Un échec ne casse rien** : tester le résultat (pas d'`ESP_ERROR_CHECK`), journaliser le nom du code, ne pas redémarrer, ne pas réessayer en boucle, laisser le service continuer.
- **Le relais est éteint** juste avant le téléchargement, y reste pendant et après un échec jusqu'à une nouvelle commande ; une demande refusée n'y touche pas.
- **On redémarre seulement après `ESP_OK`.** La confirmation de la nouvelle image et le retour arrière sont le sujet de la leçon suivante.
